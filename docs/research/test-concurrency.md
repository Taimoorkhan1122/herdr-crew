# Limiting concurrent test runs across herdr-crew agents

Research date: 2026-10-13. Scope: macOS (Darwin 25, 8 cores here), `/bin/bash` 3.2.57, Homebrew available. Where I tested a behaviour on this machine I say "tested". Where I could not confirm something from a primary source I say "unverified".

## Summary and recommendation

The need is a machine-wide counting semaphore: N test slots, every agent takes one before running a test suite, and the others wait. The smallest thing that works on stock macOS needs no daemon and no install: **one lock file per slot, taken with the built-in `lockf(1)`, wrapped in a new `herdr-crew test -- <cmd>` subcommand, plus a Claude Code PreToolUse hook that rewrites test commands into that wrapper**. A `herdr-crew tests` subcommand lists holders and waiters.

Why `lockf`: it ships with macOS (`/usr/bin/lockf`), it uses kernel `flock(2)` locks, so a killed holder frees its slot automatically (tested), it has a built-in wait timeout (`-t`), and it passes the command's exit code through (tested). Its only gap is that it locks one file, so N slots means N files and a short polling loop in bash.

### Recommended design

1. **Slots.** Default `CREW_TEST_SLOTS = max(1, ncpu / 4)`, from `sysctl -n hw.ncpu` (2 on this 8-core laptop). Reason: common runners (vitest, jest, pytest-xdist, `go test`, `cargo test`) use roughly one worker per core by default, so one run can already saturate the machine and two concurrent runs is a sensible ceiling for 8 cores. The user overrides with `CREW_TEST_SLOTS=N`. State is machine-wide, not per repo, because CPU and RAM are per machine: `${CREW_STATE_DIR:-$HOME/.herdr/crew}/tests/`. Lowering N while runs are active is safe: slot files numbered N or higher are simply no longer taken and drain naturally.
2. **Acquire.** Loop over slots i below N: `exec 9>"$dir/slot.$i"` then `lockf -s -t 0 9`; the first success wins. If all are busy, sleep about 2 seconds with a little jitter and retry until the deadline. A fixed fd number works in bash 3.2 (it has no `{fd}` allocation). Tested under `/bin/bash` 3.2.57: the fd form of `lockf` returns 0 when the slot is free and 75 (EX_TEMPFAIL) when it is held.
3. **Hold.** The wrapper runs the command as a child (not `exec`) with fd 9 inherited. The lock belongs to the open file description, so it lives as long as any process holds a copy of fd 9. Tested: when the wrapper was killed with `kill -9` while its child was still running, the slot stayed held until the child ended. This matters because the plain `lockf file cmd` form does not behave this way: when I SIGKILLed `lockf` itself, the lock was released while its child kept running, so an orphaned test would run un-throttled. Use the fd form.
4. **Stale-holder recovery.** The lock needs none: the kernel drops it when the last process holding the fd dies. A small `slot.i.info` sidecar (agent, task, pid, start epoch, command) is written after acquiring and removed on normal exit. The status view only trusts an info file when the slot's lock is actually held (probe with `lockf -s -t 0`), so a leftover file after a crash is ignored and overwritten. Waiters write `waiters/<pid>` files and are listed only while `kill -0 <pid>` succeeds.
5. **Timeout.** `CREW_TEST_WAIT` seconds, default 900 (15 minutes). On timeout the wrapper does not run the command: it prints who holds the slots and exits 75. Failing closed is deliberate, because running anyway defeats the point. The persona text says: retry once, then `herdr-crew mark <T#> blocked "test slots busy"`. Otherwise the wrapper returns the command's own exit code.
6. **Waiting costs no tokens.** The wait is one blocking shell command, not a polling loop in the model. Claude Code's Bash tool defaults to a 2 minute timeout with a 10 minute ceiling (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`; [env vars](https://code.claude.com/docs/en/env-vars)). Per the [tools reference](https://code.claude.com/docs/en/tools-reference), "When a foreground command reaches its timeout without finishing, Claude Code moves it to the background instead of stopping it", the agent is told the task ID and output file, and a moved command gets 30 minutes from the move. So a wait plus a long test run is not killed at 2 minutes; the agent is notified when it finishes (I saw the "moved to the background" message myself in this session). The hook should also set `timeout` to 600000 in `updatedInput` so most waits stay foreground. Caveat: if anyone sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, a timeout kills the command instead, and wait plus run must fit in 10 minutes. Crew must not set that variable.
7. **How agents are made to use it (three layers).**
   - Layer 1, prompt rule in the driver, navigator, tester and reviewer personas: "Run tests only as `herdr-crew test -- <cmd>`." Teaches the habit; not enforcement.
   - Layer 2, the gate: a PreToolUse command hook, matcher `Bash`, added to the `--settings` JSON that `start_agent` in bin/crew already builds (it currently passes `ctx-guard` for PostToolUse and UserPromptSubmit, so this is one more key). The script reads the hook JSON on stdin; if `.tool_input.command` looks like a test runner (npm/pnpm/yarn/bun test, vitest, jest, pytest, go test, cargo test, make test, and so on) and does not already start with `herdr-crew test`, it prints `hookSpecificOutput.updatedInput` with `command` replaced by `herdr-crew test -- bash -c <original, quoted with jq @sh>` and `timeout` 600000. The docs say `updatedInput` "Replaces the entire input object, so include unchanged fields alongside modified ones" ([hooks reference](https://code.claude.com/docs/en/hooks), PreToolUse decision control), so copy `description` and `run_in_background` through. Use the handler `if` field, for example `"if": "Bash(*test*)"`, so the process only spawns for plausible commands ([hooks guide](https://code.claude.com/docs/en/hooks-guide)).
   - Layer 3, allowlists: in `ranks/crew-inspector.md`, replace the direct `Bash(npm test *)`, `Bash(pnpm test *)`, `Bash(pytest *)` and similar entries with `Bash(herdr-crew test *)`. This is needed anyway, because Claude Code "evaluates permission rules ... against the input your hook returns, not the input Claude sent" (hooks reference), so the rewritten command must match an allowed pattern. Add `Bash(herdr-crew tests)` to the lead, manager and inspector tool lists.
8. **Visibility.** `herdr-crew tests` prints something like:

   ```
   slots 2 (CREW_TEST_SLOTS, default ncpu/4)   busy 2   waiting 1
   SLOT  AGENT                TASK  PID    AGE  COMMAND
   0     myrepo-T7-driver     T7    41233  4m   pnpm vitest run
   1     myrepo-T9-tester     T9    41990  1m   pytest -q
   WAITING
         myrepo-T8-navigator  T8    42011  3m
   ```

   Agent and task come from `CREW_AGENT` and `CREW_TASK`, which `set_env` in bin/crew already exports to every pane. The wrapper prints exactly one line to stderr when it must wait ("2/2 test slots busy: T7, T9; waiting up to 15m"), not a progress ticker, so a waiting agent's context gets one line. Append the same summary to `herdr-crew status` so the Lead and Manager see it without a new command.

### Cheap optional extras

- A slot limits how many runs start, not how hard each run hits the CPU. The wrapper can export `CREW_TEST_WORKERS = max(1, ncpu / slots)` for personas to pass to the runner (`--maxWorkers`, `-n`, `-p`, `CARGO_BUILD_JOBS`). These flags are well known; I did not re-verify them from primary docs.
- Optionally also bound slots by RAM, for example `min(ncpu/4, memsize_GB/6)`. Left out of the default to stay simple.

## Comparison of the primitives

| Option | Install and macOS | N slots? | Holder killed (stale lock) | Wait with timeout | Visibility | Exit code passthrough |
|---|---|---|---|---|---|---|
| `lockf(1)` (built in; local `man lockf`) | Already at `/usr/bin/lockf`. | One lock per file; N slots = N files plus a poll loop. | Kernel `flock`, released when the holder dies (tested). `lockf file cmd` form frees the lock if `lockf` alone is SIGKILLed while `cmd` lives (tested); fd form avoids that. | `-t seconds` (0 = try once); exit 75 on timeout. | None; needs sidecar files. | Yes (tested exit 7). 75 means busy. |
| `flock` from Homebrew (discoteq, 0.4.0, [README](https://github.com/discoteq/flock)) | `brew install flock`; README lists Darwin. Extra dependency, not installed here. | Mutex only. | Same kernel semantics. | README shows `-n`; `-w` is unverified. | None. | Yes by convention (unverified). |
| util-linux `flock` | Linux tool. Homebrew `util-linux` is keg-only and I could not confirm it installs `flock` on macOS (unverified). Upstream man page fetch returned HTTP 503. | Mutex only. | Kernel semantics. | `-w`, `-n` per upstream (unverified here). | None. | Yes. |
| `shlock(1)` (built in) | Present, but its man page says it is deprecated in favour of `lockf(1)`. | Mutex only. | PID-based: checks with `kill -0` and replaces a dead holder's lock. Good recovery; PID reuse is a small risk. | None: caller loops. | PID in file. | Not a command runner. |
| `mkdir` lock directory | Pure bash. | One dir per slot. | Not automatic: write a PID, check `kill -0`, race between check and reclaim. | Caller loops. | PID in dir. | Yourself. |
| GNU parallel `sem` (`brew install parallel` 20260922; [man](https://www.mankier.com/1/sem)) | Perl script, works on macOS; not installed here. | Yes: `sem --id NAME -j N --fg cmd`, default 1. Files in `~/.parallel/semaphores/`. | SIGKILLed-holder behaviour not in the pages I read (unverified). | `--semaphoretimeout secs`: positive = take the semaphore anyway after secs (unsafe for us); negative = exit. | No holder listing. | Unverified; without `--fg` it backgrounds. |
| `pueue` ([README](https://github.com/Nukesor/pueue), [changelog](https://raw.githubusercontent.com/Nukesor/pueue/main/CHANGELOG.md)) | `brew install pueue` 4.0.4. "MacOS is fully supported." Needs the `pueued` daemon. | Yes: groups, `pueue parallel N`. | Queue persisted and restored after a crash. Tasks run under the daemon, not the caller, so killing the caller does not stop the test. | `pueue wait`, `add --follow` (v4.0.0). No wait-timeout flag found. | Best: `pueue status` shows queue and labels. | `wait` and `follow` exit 1 on failure in some modes; passthrough of the test's own code not documented in what I read. |
| task-spooler `ts` (`brew install task-spooler` 1.0.4; [README](https://github.com/justanhduc/task-spooler)) | Bottle exists; README does not mention macOS. Needs a server on a `TS_SOCKET`. | Yes: `TS_SLOTS` or `ts -S N`. | `TS_SAVELIST` persists the job list if the server dies. | `-w` waits for a job; no timeout flag found. | `ts` lists the queue; `-o`, `-t` for output. | Shown in listing; foreground passthrough unverified. |
| `chg` and similar | Searched; no Homebrew formula named `chg`. Not pursued. | n/a | n/a | n/a | n/a | n/a |

Why not `sem` or `pueue`: `sem` adds a Perl dependency, its timeout semantics ("take it anyway") are wrong for us, and it cannot list holders. `pueue` has the best queue UI but adds a daemon to start and keep alive, runs tests outside the agent's process tree (cwd, env, `CREW_TASK`, PATH and node version must be forwarded), and returns output through `follow`. Reconsider it only if the user wants strict FIFO, a live TUI, or cross-repo queues; the `herdr-crew test` interface lets the backend be swapped later.

## What other agent tools do

- **Claude Code agent teams** ([docs](https://code.claude.com/docs/en/agent-teams)): no resource gating. Guidance is social ("Start with 3-5 teammates", "Avoid file conflicts"). Task claiming uses file locking, so file locks as the coordination primitive match this design. Quality-gate hooks exist (`TeammateIdle`, `TaskCompleted`).
- **Claude Code hooks** ([reference](https://code.claude.com/docs/en/hooks), [guide](https://code.claude.com/docs/en/hooks-guide)): PreToolUse can allow, deny, ask, defer, or rewrite arguments with `updatedInput`; exit code 2 blocks and stderr becomes the reason. Matching hooks run in parallel; if several return `updatedInput`, the last to finish wins and the guide says to avoid more than one hook modifying the same tool's input.
- **Conductor** ([worktrees](https://www.conductor.build/docs/concepts/git-worktrees)): one worktree per workspace; ports are separated with `CONDUCTOR_PORT`. I found no CPU or test throttling.
- **vibe-kanban** ([Byteiota write-up](https://byteiota.com/vibe-kanban-orchestrate-ai-coding-agents-10x-faster/), anecdotal): worktree per agent; claims about 4 concurrent agents is the practical limit before CPU and memory contention. No gating mechanism, and the number is unmeasured.
- **container-use (Dagger)** ([blog](https://dagger.io/blog/agent-container-use)): each agent gets its own container and git branch, with content-addressable caching so repeated work stays fast. Container CPU limits were not mentioned in what I read. Containers isolate files and tooling but do not by themselves cap total host CPU.
- **Nx and Turborepo**: per-invocation caps only. Nx `--parallel=N` or `nx.json` ([docs](https://nx.dev/ci/concepts/parallelization-distribution)); Turborepo `--concurrency` (default 10, accepts `50%`) ([reference](https://turborepo.dev/docs/reference/run)). They do not coordinate across separate processes, so N agents each running turbo still multiply. Remote caches reduce repeated test work and are a complementary lever.
- **Bazel**: `--local_test_jobs` caps concurrent local tests ([commit](https://bazel.googlesource.com/bazel/+/dffb6ee9dbf19e47b65c50c5f1955014e1e8f68c), [jmmv.dev](https://jmmv.dev/2019/12/bazel-local-resources.html)). My inference is that it is per Bazel server, so separate worktrees would not share the cap.
- **claude-squad, Crystal, Sculptor, OpenHands, Codex cloud, Devin**: my searches found nothing on test concurrency control for claude-squad or Crystal, and I did not research the others. Cloud products avoid the problem by giving each task its own VM or container, which is not an option on one laptop.

## Risks and open questions

- **Command detection is heuristic.** A regex catches `npm test`, `vitest`, `pytest` and so on, but not `make check`, `./gradlew test`, `npm run ci` or `verify.sh`. Mitigation: an extended-regex override (`CREW_TEST_PATTERNS`) plus the prompt rule and the narrowed inspector allowlist.
- **Whole-command wrapping.** Wrapping `cd x && pnpm test | tail -20` holds the slot for the cheap parts too and changes quoting. Acceptable, but test that `cd` and env behave as before inside `bash -c`.
- **`updatedInput` without a decision.** The docs say `updatedInput` can be paired with `allow` (auto-approve) or `ask` (show the modified input), and that deny and ask rules are still evaluated. What happens with `updatedInput` and no `permissionDecision` is unclear to me; test once. Also unverified: exact merge behaviour of `--settings` hooks with the user's global hooks. All matching hooks run, but rewrites race (last finisher wins). Check `~/.claude/settings.json` for any other hook that rewrites Bash commands before shipping; there must be exactly one rewriter.
- **Hook timeout.** Command hooks default to 600 s and a timed-out PreToolUse hook does not block the call. Keep the hook fast (jq plus a regex) and do all waiting in the wrapper.
- **No fairness.** Polling is not FIFO, so an unlucky waiter can starve. Fine for a handful of agents. If needed, add ticket files (`waiters/<epoch>-<pid>`) and let only the oldest live waiter take a free slot.
- **A hung holder pins a slot** (watch-mode run, `vitest` without `run`). Mitigations: a hold limit (`CREW_TEST_MAX_RUN`, default 20 min, under the 30 min background limit), AGE column in `herdr-crew tests`, and an optional `herdr-crew tests --kill <slot>` for the Manager.
- **Process-group kill is unverified.** I confirmed an inherited fd keeps the slot while an orphaned child lives. I did not verify whether Claude Code kills the whole process group when a background command hits its time limit; either outcome is safe for the slot.
- **Other contention classes** (e2e browsers, DB-backed tests, ports) share one pool at first. A named pool (`CREW_TEST_POOL=e2e`) is cheap to add because a pool is just a directory.
- **Open questions for the user:** (1) Is ncpu/4 (2 here) right, or should one core group stay free for your own work (then 1)? (2) Is failing closed after 15 minutes acceptable, or should a timed-out agent run anyway? (3) Hook rewriting (transparent, heuristic) plus explicit wrapper, as recommended, or wrapper only? (4) Should lint, typecheck and build also take a slot, or only tests?
