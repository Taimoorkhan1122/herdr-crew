# Rewire herdr-crew onto core and app

The migration is feasible, but it is a control-plane rewrite, not a dependency swap. `bin/crew` makes **30 direct `herdr` calls** across topology, agent lifecycle, inspection, workspace selection and pane metadata ([bin/crew](../bin/crew)). `herdr-core` (`hc`) supplies the process and agent layer, while `herdr-app` supplies the spaces, tabs and panes that `hc` deliberately does not model. The split is clean enough to rebuild the launcher, but four contracts have no direct replacement: per-pane environment injection, agent-to-pre-created-pane binding, shell-foreground detection for restart, and pane metadata/titles. A fifth, message delivery to a blocked agent, changes from "send anyway" to "refuse and require a person". The recommended design is app-owned layout with `hc`-owned control: the app creates the visible frame and returns terminal IDs, and `hc` handles send, wait, read, status, events and cleanup. The app becomes mandatory for `launch`, `team` and `close`, which excludes headless server use. No live crew was launched during this research, so every timing and ID-handoff claim below remains contract-level until the validation spikes in the final section pass.

## The old runtime is maintained, so this is a product choice

The vendor has not deprecated the legacy `herdr` multiplexer. It shipped **0.9.5** as a hotfix, its repository was pushed on 2026-11-01, and it still has its own site, plugin gallery and stable/preview channels ([herdr TUI](https://herdr.dev/tui/), [herdr repository](https://github.com/herdrdev/herdr)). The new stack is a separate product line: `herdr-app` is the window, `hc` is the headless runtime, and the app explicitly says `hc` "is not `herdr`, the older terminal multiplexer" (`hc --skill`). The homepage and download page now lead with the desktop app, and `herdr-app` was created on 2026-10-16, but no announcement, roadmap item or end-of-life statement connects the two lines ([herdr.dev](https://herdr.dev), [herdr-app repository](https://github.com/herdrdev/herdr-app)).

That matters for sequencing. A full replacement is justified by capability, not by an upstream deadline. The new stack adds **`hc wait --children`**, a typed event stream, labels, templates with first-message delivery results, remote machines, and a desktop layout layer. It also removes things the crew currently depends on. If the goal is only to reduce maintenance, staying on the maintained TUI is defensible. If the goal is the desktop app and the newer orchestration primitives, migrate, but plan for a coordinated rewrite across the launcher, fixtures, prompts, permissions and docs rather than a rename.

The versioning relationship is weak. App and core update independently: this machine runs **app 0.1.11 with core 0.1.16**. The app updates core to "the latest release of the same generation", but no compatibility matrix, minimum core version or schema guarantee is published ([herdr-app changelog](https://github.com/herdrdev/herdr-app/blob/master/CHANGELOG.md), [`herdr-app/AGENTS.md`](file:///Users/gok/.config/herdr-app/AGENTS.md)). herdr-crew can check both binaries at startup, but it cannot pin what users receive.

## Two runtimes split one job: hc runs processes, the app runs layout

`hc` has no workspace, tab or pane objects. It has terminals, addressed as `t7` or by name, with labels, parent-child links, status from OSC 7501, and an OpenRPC socket API (`hc schema`). `herdr-app` has spaces, tabs, panes, splits, layouts and mods, and drives them through `herdr-app do <command>` against a running window. The app-created terminal is still a core terminal, so the two layers meet at the terminal ID.

| Legacy `herdr` use | Target command | Replacement quality |
|---|---|---|
| `workspace list/create` | `herdr-app ls`; `herdr-app do space.new --name ... --folder ...` | Workaround: no workspace label, resolve space by name or folder |
| `tab create/list/close` | `herdr-app do tab.new`; `herdr-app ls`; `do tab.close --id` | Workaround: close by resolved ID, not label |
| `pane split --ratio` | `herdr-app do pane.split --direction right\|down` | Partial: binary splits only, no ratio argument |
| `pane run tsk` | `tab.new`/`pane.split` with `--argv '["tsk"]'` | Clean if argv is used |
| `agent start --pane` | App `tab.new`/`pane.split` with agent argv, or `hc run` | Not equivalent: `hc run` always creates a new terminal |
| `agent prompt` | `hc send <t> <text>` | Partial: refuses when blocked unless `--force` |
| `agent wait --until ...` | `hc wait <t>`, `hc wait --children` | Partial: no per-status selector |
| `agent read --source` | `hc read <t> --lines N` | Mostly clean, source selection disappears |
| `agent get/list` | `hc get <t>`, `hc ls --json` | Clean, terminal-centric instead of agent-centric |
| `agent send-keys` | `hc keys <t> enter` | Clean |
| `agent rename --clear` | No rename; live-name uniqueness only | Gap: remove or kill the finished terminal instead |
| `pane process-info` | No process-group API | Gap: cannot prove the pane returned to its shell |
| `pane report-metadata --title` | `do tab.rename --id`; OSC title from inside the terminal | Partial: tab title is reliable, pane title is indirect |
| `status` / `watch` polling | `hc ls --json`; `hc events` | Cleaner: one call or a stream instead of name probes |
| `HERDR_ENV` / `HERDR_WORKSPACE_ID` | `herdr-app status` / app IDs; `HC_TERMINAL_ID` | Gap: no workspace environment contract |

The app's own docs describe the visibility protocol: a terminal opts into the window with **`herdr.space=<id>`** and optionally **`herdr.tab=<id>`** labels; unlabeled terminals stay hidden, and an unknown ID creates an unnamed space or tab ([`herdr-app/AGENTS.md`](file:///Users/gok/.config/herdr-app/AGENTS.md), [herdr-app skill](https://github.com/herdrdev/herdr-app)). `hc get` exposes those labels, which gives the launcher a stable cross-reference between core terminals and app placement. `herdr-app ls` returns the full space → tab → terminal tree with `sp*`, `tb*`, `pa*` and `t*` IDs, and `hc ls --json` adds terminal state, name, cwd, status and labels.

## Eight gaps decide the architecture

**Environment injection is gone.** The launcher passes seven `CREW_*` values as per-pane `--env` arguments because a split does not inherit the tab environment ([bin/crew:93-99](../bin/crew), [docs/STATE.md:64](../docs/STATE.md)). `hc` has no `--env`; it inherits the caller's environment and offers `--label` separately. The app's `tab.new`/`pane.split` accept `--argv` but no environment map. The workable replacement is an explicit `env CREW_SLUG=... CREW_TASK=... <agent>` argv prefix. That keeps hooks and `herdr-crew mark` working, but it turns identity from ambient state into command-line state. `HERDR_ENV` and `HERDR_WORKSPACE_ID` must be replaced by an app probe and a saved space/tab ID.

**Agent-to-pane binding no longer exists.** `herdr agent start <name> --pane <pane>` attaches a named agent to an existing shell pane ([bin/crew:269-277](../bin/crew)). `hc run` always creates a new terminal. The target design must therefore let the **app** start the agent through `tab.new` or `pane.split` with `--argv`, then use `hc send`/`wait`/`read` against the returned terminal ID. The coupling audit's alternative, create with `hc run` and then attach with labels, is the fallback if app-started argv proves unreliable.

**Blocked now means stop.** `herdr agent prompt` delivered text and the launcher retried Enter when the paste did not submit ([bin/crew:219-234](../bin/crew)). `hc send` returns exit **9** and refuses when the agent is blocked on a permission or question, unless `--force` is used (`hc --skill`). That refusal is a safety boundary. `say` must report "agent needs a person" and preserve the message in tsk, not bypass it. The same applies to first-message delivery: `hc run` returns `first_message.sent: false` when the agent is not ready, and the launcher must read the screen before retrying.

**Restart cannot preserve the same pane by waiting for a shell.** The current restart sends `/exit`, polls `pane process-info` until the foreground process group equals the shell PID, then starts the agent again in that pane ([bin/crew:603-641](../bin/crew)). `hc` exposes no foreground process-group query. Worse, the app closes a terminal pane when its program exits; `hc keep` recovers a **lost** terminal with a shell, not a normal exit. There are two honest options: accept a new pane/terminal on restart, or wrap every agent in a keep-alive shell that execs the agent and returns to the shell on exit, then restart by sending the saved command to that shell. The wrapper preserves pane identity but adds a shell layer and makes status depend on the agent's OSC reports rather than the terminal's own program. This is the largest behavioral decision in the migration.

**Pane titles and progress metadata are partial.** `herdr pane report-metadata ... --title "T7 driver: started"` has no equivalent ([bin/crew:476](../bin/crew)). The app can rename a **tab** with `do tab.rename --id <tab> --name ...`; that is a mutator but reliable. A **pane** title comes from the program's OSC title sequence, which the app renders from `panes()[].title`. A crew can write `\033]0;T7 driver: started\007` to its own tty as a best effort, but it is not a documented API. The practical replacement is tab-level titles for task progress and labels for machine-readable state; accept that the old per-pane title cue changes shape.

**Space identity and close-by-label need a new contract.** Outside a Herdr pane, the launcher reuses or creates a workspace labelled `crew-<slug>` and `close` finds tabs by label prefix ([bin/crew:202-215](../bin/crew), [bin/crew:505-515](../bin/crew)). The app has no tab labels; `close` must resolve IDs from `herdr-app ls` by matching tab names. The saved `CREW_WS` field becomes a space ID plus tab IDs. Reusing a crew space across launches is still possible by matching the space name or folder, but it needs a cache with an `ls` revalidation, not a single environment variable.

**Process lifetime changes.** `hc` terminals started by a launcher are children of that terminal and die with it unless `--outlive-parent` is set (`hc --skill`). App-created terminals belong to the running app and survive launcher exit. Any `hc run --bg` used for the board or background work must either use `--outlive-parent` or be replaced by an app-created terminal. This is easy to miss because a quick test with the launcher still running will pass.

**Headless use is excluded.** The app is a desktop GUI: Apple Silicon macOS in the shipped build, Linux x86-64/ARM64 with a desktop session and Vulkan, Windows x64 ([herdr-app README](https://github.com/herdrdev/herdr-app)). Core runs headless on all three, but `herdr-app ls`, `status` and `do` need a running window. "App required" therefore means a Linux server, container or CI box cannot run `launch`, `team` or `close`. The docs must state that explicitly, or the project must keep an `hc`-only degraded path, which contradicts the chosen full replacement.

The status vocabulary also changes: `unknown` disappears, `error` appears, and plain programs report no status at all. `hc ls` replaces the per-name probe loop in `status` and `watch` with one call, which is a genuine simplification. `hc events` can replace polling with a filtered stream, but it is a long-running subscription and should be a second-step improvement, not a prerequisite for the first working migration.

## Architecture: let the app build the frame, hc control the crew

Three designs fit the evidence.

**Option A, app-owned frame with hc control (recommended).** Preflight requires `hc`, `herdr-app` and a reachable window. Resolve or create the crew space with `herdr-app ls`/`space.new`. Create the Lead tab with `tab.new --space <id> --name "crew <slug>" --argv '["env","CREW_SLUG=...",...,"claude", ...]'`; split right for the Manager and down for the board, each with its own argv. Keep the returned `{pane, terminal}` IDs. All later talk uses `hc send`, `wait`, `read`, `keys`, `get`, `ls` and `kill`. The board is `argv ["tsk"]` in its own pane. `close` resolves tab IDs from `herdr-app ls` and calls `do tab.close --id`. This preserves the current "topology exists before the agent starts" ordering, gives every visible terminal an app-owned lifetime, and keeps environment injection explicit in argv. Its weaknesses are app-created-terminal argv limits, unknown first-task delivery guarantees, and no split-ratio control.

**Option B, hc-owned terminals adopted by the app.** Start everything with `hc run --bg --outlive-parent --name ... --label herdr.space=... --label herdr.tab=...`, then let the app adopt and arrange the terminals. This gives the strongest launch contract (`first_message.sent`, readiness reasons) and keeps orchestration usable without app `do` calls after creation. It is weaker on layout: adoption may create tabs or panes in an order the launcher does not control, and building a specific 2×2 frame from labels alone is unproven. It is the fallback if Option A's argv or task delivery fails.

**Option C, a crew mod.** A herdr-app mod renders the board and crew status, reads `spaces()/tabs()/panes()/agents()/terminals()`, and calls `run()` or `hc()`. This is the best long-term UI, but it expands the trusted-JS boundary, requires `herdr-app check` plus screenshot validation, and does not solve launch, environment or restart. Treat it as a later enhancement, not the migration vehicle.

Option A is the recommendation because it keeps the current lifecycle shape and the smallest number of moving parts. It also makes the app dependency honest: if the window is unavailable, `launch` fails before creating a tsk task, rather than half-building a crew.

The 2×2 frame remains approximate. `pane.split` accepts only `right` or `down`; there is no ratio argument. The app exposes `layout.resize` on layout nodes and stores click geometry in `layouts/.state`, but `herdr-app ls` returns a flat terminal list with no geometry, so the launcher cannot verify the arrangement. The current board split at 0.3 becomes the app's default divider, and the human can drag it. Ship the frame as a starting point, not a guarantee.

## What breaks for users, and what must change together

Onboarding changes first. Users need `hc` and the desktop app instead of "Herdr with the `herdr` command on PATH" ([README.md:44-49](../README.md)). `tsk setup herdr` and `herdr server reload-config` stop applying, because `tsk`'s integration is a legacy-Herdr plugin with `prefix+t` and `prefix+a`; `tsk` has no `hc` or app target, and its TUI still runs in any terminal ([tsk README](https://github.com/smarzban/tsk), [tsk setup on this machine](file:///Users/gok/.config/herdr/plugins.json)). The board therefore becomes a plain `tsk` terminal. The old keybindings and dispatch integration are lost, but herdr-crew already dispatches through its own launcher, so the practical loss is smaller than for a standalone tsk user.

The agent contracts are runtime permissions, not prose. The Manager's `agent.json` grants `Bash(herdr agent wait|read|get|list *)`, and its prompt tells it to run `herdr agent wait ... --until done` ([agents/crew-manager/agent.json](../agents/crew-manager/agent.json), [agents/crew-manager/AGENTS.md:48](../agents/crew-manager/AGENTS.md)). Those grants must become `hc wait`, `hc read`, `hc get`, `hc ls` in the same change as the prompt. A grep-only rename will miss semantic differences such as `--until blocked`, `--source recent-unwrapped`, and the blocked-send refusal. `SKILL.md`, `docs/features.md`, `docs/STATE.md`, ADRs 0002, 0007, 0012, 0014 and 0015, and the user-facing error that names `herdr` all describe behavior that will no longer exist ([SKILL.md](../SKILL.md), [docs/features.md](../docs/features.md), [docs/adr](../docs/adr)).

The tests break at once, not at the edges. The fake `herdr` in `test/dry-run.sh` is sourced by `partial-init.sh` and `test-hook-integration.sh`, and `test/project-launch.sh` asserts per-pane environment captured from `--env` ([test/dry-run.sh:17-88](../test/dry-run.sh), [test/project-launch.sh:24-35](../test/project-launch.sh)). A compatibility shim named `herdr` would let the suite pass while production is broken. Replace the fake with `hc` and `herdr-app` fakes in the same change that rewrites the launcher, and add state for app space/tab IDs, terminal status transitions, a blocked terminal, and the ready-vs-not-ready launch result. Keep the tsk and git fakes; they are the stable half of the system.

`tsk` and `git` themselves should not change. Worktree creation, branch rules, task state and handoff files are independent of the runtime ([bin/crew:349-408](../bin/crew)). The non-atomic `mark` path remains: tsk status, tsk step and pane metadata are three calls, and the third one now becomes a tab rename or label update. Do not widen that atomicity bug during the migration.

Storage paths can stay `~/.herdr/crew/<slug>` and `~/.herdr/worktrees/<slug>` to avoid a second migration. They are implementation paths, not the product surface. If the project renames them, do it as a separate, reversible step with a fallback reader.

## Verify five things before committing to the rewrite

The source and help text settle API shape, not timing or ID handoff. Five disposable checks remove most of the remaining risk, all under an isolated `HC_SESSION` and scratch XDG paths so the user's live terminals are untouched (`hc --skill`).

First, create a disposable app tab with `herdr-app do tab.new` and confirm the returned terminal is immediately visible to `hc ls`/`hc get`, with a stable `t*` address. Second, launch an agent with a long argv plus an `env CREW_*` prefix and confirm the environment reaches the agent and its shell commands. Third, watch `hc get` from launch through readiness for 30 seconds and confirm the status sequence matches the old `agent start` expectations, including what happens when the agent shows a trust dialog. Fourth, send to a blocked agent without `--force` and confirm exit 9 is distinguishable from "terminal missing" exit 3. Fifth, kill an agent and confirm whether the app pane closes, whether `hc keep` recovers a shell, and whether a keep-alive shell wrapper can restart the agent in the same terminal.

If checks one through three pass, Option A is viable. If app-started argv or first-task delivery fails, fall back to Option B and accept weaker layout control. If the restart check fails both ways, document "restart creates a new pane" as a user-visible behavior change rather than claiming parity.

The build order is forced by the dependencies: **fixtures → environment/identity → topology → agent start → messaging/wait → restart/close → prompts/docs**. Fixtures gate every suite, environment is set before topology, topology precedes agent start, and agent start precedes submission ([bin/crew:93-99](../bin/crew), [bin/crew:329-345](../bin/crew), [bin/crew:219-234](../bin/crew)). Doing agent start first leaves no terminal to start in. Doing docs first advertises behavior that does not exist.

## Conclusion

The migration buys a real orchestration layer: one `hc ls` or event stream instead of name probes, explicit first-message delivery results, `wait --children`, labels, remote machines, and a desktop layout surface. It costs the per-pane environment contract, pane-title metadata, same-pane restart, headless deployment, and the tsk `prefix+t` integration. Those are not cosmetic losses, and three of them change user-visible behavior.

The decisive question is not whether `hc` can replace `herdr`; it can for process control. The decisive question is whether the crew should own a desktop app dependency and a keep-alive shell wrapper to preserve pane identity. If the answer is yes, Option A with the five validation spikes is the lowest-risk path. If the answer is no, the maintained TUI remains a valid runtime, and the honest recommendation is to defer the migration rather than ship a half-equivalent control plane.
